# 設計原則：状態・性質ファースト（State & Property First Design）

> 参照元思想：「操作より状態・性質に着目する」（ナレッジワーク CTO mayah）

---

## 0. このドキュメントの使い方

このファイルは Claude Code が設計・実装作業を行う際に参照する設計原則集です。
CLAUDE.md から `@docs/design-principles.md` で呼び出して使用します。

新機能追加・既存機能変更・コードレビューのすべての場面で、
**セクション 1 → 2 → 3 の順序を必ず守ること。**

---

## 1. 実装前に必ず行う：状態・性質の定義

実装（コードを書くこと）を始める前に、以下のテンプレートを作業コメントとして書き出す。
これを省略してコードを書き始めることを禁止する。

### 定義テンプレート
```
## 状態・性質定義

### 対象
（何の機能・関数・モジュールか）

### 性質（不変なもの）
- （例）ファイル種別は作成後に変わらない
- （例）ユーザーIDはシステム内で一意である

### 操作前の取り得る状態（網羅すること）
- [ ] 状態A：〜〜な状態
- [ ] 状態B：〜〜な状態
- [ ] 状態C：〜〜な状態

### 操作後の取り得る状態（成功時は可能な限り1つに絞る）
- [ ] 状態X：〜〜な状態（これ以外はすべてエラーとして扱う）

### 不変条件（Invariant）
- 操作の前後を通じて常に成り立つべき性質を列挙する
- （例）有効なユーザーのメールアドレスは常にユニークである
```

---

## 2. 状態と性質の定義と区別

### 定義

| 概念 | 定義 | 例 |
|------|------|-----|
| **性質** | 対象に紐づく不変なもの | `fileType`, `userId`, `createdAt` |
| **状態** | 時間とともに変化しうるもの | `isUploaded`, `isActive`, `status` |
| **操作の可否** | 状態と性質の合成結果。状態でも性質でもない | `canConvert`, `isEditable` |

### 状態と性質が混ざると何が起きるか

- 性質のみに依存する処理は、他の場所で何が起きても影響を受けない
- 状態が混ざった瞬間に、その処理は「状態を変化させる別の処理」に依存する
- 調査・デバッグの対象範囲が指数的に広がる
- 「変換できるはずなのにできない」といった再現困難なバグの温床になる

## 3. 実装時のルール

### 思考の順序（必ず守る）
```
1. 操作前に取り得る状態を列挙する（漏れなく）
2. 操作後に取り得る状態をできる限り1つに絞る
3. 不変であるべき性質（Invariant）を明示する
4. 上記を満たすための操作（実装）を考える  ← ここで初めてコードを書く
```

### 禁止事項

| 禁止 | 理由 | 代替 |
|------|------|------|
| 「ただし書き」の安易な追加 | 状態の複雑さが積み重なり、読む側のコストが増大する | 状態定義を見直してただし書きが不要な設計にする |
| 操作後に「あり得てはいけない状態」を放置 | 後続処理で予期しない挙動を引き起こす | 型・バリデーション・即時エラーで排除する |
| if/else を増やして状態の複雑さを隠す | 見えない状態が増え、変更困難になる | 状態を先に整理してif/elseを減らす設計にする |
| 操作の都合に合わせて仕様を決める | コードが簡単になる代わりに状態が複雑になる | 状態・性質の定義から仕様を逆算する |

### やむを得ず「ただし書き」が必要な場合

コードに以下のコメントを必ず記載する。
```
// [EXCEPTION] ただし書き理由：〜〜のため、〇〇の場合は状態を変更しない
// 本来は〜〜という設計が望ましいが、〜〜の制約により現状この実装とする
```



## 4. 自己レビューチェックリスト

コードを書いた後、提案・出力する前に以下を確認する。

### 状態の健全性
- [ ] 操作後に「意図しない状態」が存在し得ないか？
- [ ] 「ただし書き」なしに事後条件が一意に定まるか？
- [ ] 型・構造体で不正な状態を表現不可能にできているか？

### 状態と性質の分離
- [ ] 関数の引数に「状態」と「性質」が混在していないか？
- [ ] 「操作の可否」を状態・性質と同一視していないか？
- [ ] 状態に依存する処理と性質に依存する処理が分離されているか？

### 設計の健全性
- [ ] 操作の都合に合わせて状態を複雑にしていないか？
- [ ] 埋め合わせのif文が増えていないか？
- [ ] 変更・デバッグ時の調査範囲が不必要に広がっていないか？

## 5. 背景・参考

この設計原則は以下の考え方をベースにしています。

- **契約プログラミング（Design by Contract）**：Bertrand Meyer 提唱。事前条件・事後条件・不変条件の明示
- **宣言的設計**：How（操作）より What（あるべき状態）を先に定義する
- **関数型プログラミングの思想**：状態をミュータブルにせず不変性を優先する
- **セキュア・バイ・デザイン**：安全な状態遷移を設計の中心に置く
- **DDD の不変条件（Invariant）**：ドメインモデルが常に満たすべき性質の明示

詳細は以下の記事を参照：
- https://zenn.dev/knowledgework/articles/c48539d2f35ecc
- https://zenn.dev/knowledgework/articles/95f30cfd155b5d
