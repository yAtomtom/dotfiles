## 設計 / 実装のルール

### 変更容易性 / モジュラー性
- 凝縮度，結合度は採用せず，カプセル化と関心の分離を判断基準とする
- カプセル化とはgetter, setterを定義することではなく，データと操作ロジックをひとまとめにすることを指す

### 契約による設計（DbC）
- 事前条件・事後条件・不変条件（クラス不変条件，ループ不変条件）を定義せよ

### インターフェースと実装の分離
- インターフェースは実装と分離し，本来関心をもつべき引数のみ受け取る
- ログ・通知用の時刻/ユーザー情報等はより上位のレイヤーで吸収する

### DDD
- コアドメインに集中的に開発コストを投じ，ドメインごとにロジックを隔離する

### 目的駆動プログラミング
- 目的（目指すべき状態）・目標（仕様/制約）・手段（コード）は1対1対1
- 目的が決まる前に手段を決定しない．目的に対して手段は一意に定める

### 関数型プログラミング
- メソッドは純関数を尊重し，Timeなど動的なものは内部に持たずに引数として受け取る

### イミュータブル設計
- 完全コンストラクタ: インスタンス変数は初期化時にすべて行い，それ以降の変更は許されない
- イミュータブル設計: 生成後に値が確定し変更されないオブジェクト（結果，出力，差分，設定スキーマ等）は言語の機構でイミュータブル性を強制する

### KISS原則
- テクニックを使う前に，その必要性を疑え．バグが減らないなら細かい書き方の指摘はするな

### 判断の原則
- ルールは状況・コンテキストに依存する（言語ゲーム）．変更容易性と整合保全性の担保を優先
- 設計・実装の判断に迷った場合は保守性（変更容易性と可読性）を優先せよ
- 指示内容または使用するテクニックの数が5つ以上を超える場合，仕様や要件を疑ってそこで指示を中断し，使用者の指示を仰げ

### テスト駆動
- テスト対象となるメソッドが直接的に参照しているものはモック，スタブを行わない
- モック，スタブはテストの関心がないが動作するために行うものであり，極力行わない

### コメント
- コードでは伝わらないビジネスユースケースの背景を冗長でなく簡潔に書く．命名・型・シグネチャ・テストから自明のものは不要
- 型が表現している契約をコメントで再説明しない（例: `Required<...>` に「必須である」旨のコメントは不要）
- 変更の根拠・正当化（他レイヤーの実装詳細の引用を含む）はコメントではなくコード外の成果物（コミットメッセージ / PR 説明 / レビュー報告等）に書く．実装詳細の引用は実装変更で陳腐化する

### DRY原則と抽象化
- DRY原則に従う場合は必ず抽象化を行う．抽象化ができない，または恩恵が少ない場合はDRYにしない

### エラー検知（Raw Data Now）
- Fallbackは現象を隠蔽するので不要．余計な整形をせずに生データを表示する

## サンドボックス
- 設計ドキュメントや一時的な出力ファイルは自身のサンドボックスに配置せよ
  - Claude: `~/claude-sandbox/`
  - Copilot: `~/copilot-sandbox/`
- ファイル名はタスクの内容が識別できる命名にせよ（例: `design_<feature_name>.md`）

### クロスレビュー
チェックリストの指定タイミングにて，対となるエージェントによるレビューを実行せよ。

| 実行者 | 出力先 | レビュアー | コマンド |
|--------|--------|------------|----------|
| Claude | `~/claude-sandbox/` | Copilot | `command copilot --model "gpt-5.5" --effort "xhigh" --add-dir $HOME/claude-sandbox/ -p "~/claude-sandbox/<出力ファイル名> をレビューしてください"` |
| Copilot | `~/copilot-sandbox/` | Claude | `command claude -p "~/copilot-sandbox/<出力ファイル名> をレビューしてください" --allowedTools "Read,Glob,Grep"` |

## 実行の手順

### 実行Tierの判定

タスク着手前に以下の基準でTierを判定し，対応するチェックリストの範囲を実行せよ．
判定が困難な場合はTier 3を選択するか，使用者に確認せよ．
なお「ドメイン層のクラス・メソッドに変更があるか」を一次判定の軸とし，該当する場合はTier 2以上とせよ．

| Tier | 対象の変更規模 | 例 |
|------|--------------|-----|
| 1 | 軽微な修正 | タイポ・定数・文言・コメントの修正 |
| 2 | 中規模の変更 | 既存機能の仕様変更・リファクタリング・バグ修正 |
| 3 | 新機能・大規模変更 | 新ドメイン追加・アーキテクチャへの影響がある変更 |

---

### チェックリスト（Tier 1）

- [ ] テストを作成し動作を確認せよ
- [ ] 動作が失敗する場合に実装の変更が必要な場合は，確認または指示を伺え
- [ ] Linter, Formatterを実行せよ

---

### チェックリスト（Tier 2）

- [ ] 既存のコアドメインと境界付けられたコンテキストとの整合を確認せよ
- [ ] 目的駆動プログラミングにより実装すべき機能を整理せよ
- [ ] 機能についてインターフェースの整理し，契約による設計によって条件を整理せよ
- [ ] 機能について変更容易性の観点からカプセル化と関心の分離が担保できているか確認せよ
- [ ] KISS原則に則り関数型プログラミングの思想に基づいて実装せよ（コメントは「コメント」規約の範囲に限る）
- [ ] 判断の原則に基づいて状況，コンテキストに応じた実装を行いつつも，複雑性が増大する場合は指示を伺え
- [ ] 設計・実装の判断に迷った場合は保守性（変更容易性と可読性）を優先せよ
- [ ] テストを作成し動作を確認せよ
- [ ] 動作が失敗する場合に実装の変更が必要な場合は，確認または指示を伺え
- [ ] 指示通りに実装を変更した場合は，DDDに基づく設計に矛盾がないか確認せよ
- [ ] テストが通った場合にLinter, Formatterを実行せよ
- [ ] 設計への影響がある場合はサンドボックスに差分を出力しクロスレビューを実行せよ．**プランモード中の場合はクロスレビューを実行せず，プラン承認後に実施すること（Bash実行によりプランモードが自動解除されるため）**．問題がある場合は確認または指示を伺え
- [ ] 変更があった場合は，チェックリストの最初から改めて確認せよ（同一項目で2回以上変更が発生した場合は使用者に確認）

---

### チェックリスト（Tier 3）

Tier 2のチェックリストに加え，以下を実行せよ:

- [ ] DDDに基づきコアドメインと境界付けられたコンテキスト（目的）を設計せよ
- [ ] 設計の内容をサンドボックスにファイルとして出力し，クロスレビューを実行せよ（Tier 2チェックリスト実行前）．**プランモード中の場合はプラン承認後に延期せよ**
- [ ] Tier 2チェックリスト完了後，設計内容をサンドボックスから確認し最終ドキュメントを出力せよ

## MCP 書き込み操作の確認

MCP の書き込み操作 (Notion / Slack / Figma / GitHub 等で「create」「update」「delete」「post」「move」「patch」を含むツール) を呼ぶ前に、対応 docs を必ず参照して確認手順を踏むこと:

- Notion: `.claude/docs/mcp/notion.md` — Level 2/3 の確認・破壊操作ポリシー
- Slack: `.claude/docs/mcp/slack.md` — 投稿前の対象チャンネル・全文確認
- Figma: `.claude/docs/mcp/figma.md` — ツール選択と制約
- context7: `.claude/docs/mcp/context7.md` — ライブラリ ID / バージョン特定手順

PreToolUse hook (`pretooluse-guard.sh`) が代表的な書き込みツールを deny するが、これは二重防御の片側であり、ガイダンス確認は省略しない。

## rtk (Rust Token Killer)

トークン削減プロキシ。Bash 操作で `rtk gain`（節約量分析）・`rtk discover`（節約機会の発見）・`rtk proxy`（生コマンド）等のメタコマンドを使う際は `.claude/docs/rtk.md` を参照する。通常のコマンドは PreToolUse hook が透過的に `rtk` へリライトするため、明示的に意識する必要はない。
