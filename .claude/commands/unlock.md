---
description: "Plan lock を解除する（オプションで unlock 後の指示を引数として受け取る）"
---

Plan lock の解除は UserPromptSubmit hook (`userpromptsubmit-unlock.sh`) が処理しています。

ただし hook が無効化されている可能性（jq 不在等）もあるため、必ず lock の実在を確認してから報告してください:

1. Bash で `ls /tmp/.claude-plan-lock-* 2>/dev/null; ls /tmp/.claude-plan-lock 2>/dev/null` を実行し lock の有無を確認する
2. lock が存在しない場合 → ユーザーに「plan lock を解除しました。Edit/Write が使用可能です。」と報告する
3. lock がまだ存在する場合 → ユーザーに「lock が残っています: <該当パスを全て列挙、件数も明示>。端末で `! rm <ファイルパス>` を実行してください」と報告する（hook で消せなかった原因として jq 不在や権限不足を疑うこと）。**この場合は後述の引数の有無に関わらず実装に着手せず停止する**

unlock 後の指示: $ARGUMENTS

上記「unlock 後の指示」の判定基準（ユーザー入力の文意ではなく、文字列が以下のいずれに該当するかで機械的に判定すること）:

- **A. 引数なし扱い**: 次のいずれかに該当する場合のみ。実装作業を始める前にユーザーの明示的な指示を待つ。
  - 完全な空文字列
  - 空白文字のみ
  - 文字列 `$ARGUMENTS` がリテラルとしてそのまま残っている状態（Claude Code が展開しなかったケース）
- **B. 引数あり扱い**: 上記 A に該当しない、何らかの有意な文字列が入っている場合（例: 「実装して」「typo を直して」「PR を作って」など、内容の具体性や曖昧さは問わない）。ユーザーからの明示的な実装指示として扱い、lock 解除を報告したうえで続けて実装に着手する。
- **C. lock 残存時の例外**: A/B の判定に関わらず、lock が残存している場合は実装に着手しない（lock 解除失敗の原因究明をユーザーに案内することを優先する）。

注意: ユーザーが渡した文字列が「短い」「曖昧」「指示として弱い」と感じても、それを理由に A に分類しない。A は形式的に空・空白・未展開リテラルの 3 パターンのみ。
