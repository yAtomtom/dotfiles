# slack MCP アクセスポリシー

## Level 1: 確認不要（自由にアクセス可能）

読み取り専用。副作用なし。

| ツール | 用途 |
|---|---|
| `slack_list_channels` | チャンネル一覧の取得 |
| `slack_get_channel_history` | チャンネルのメッセージ履歴取得 |
| `slack_get_thread_replies` | スレッド返信の取得 |
| `slack_get_users` | ユーザー一覧の取得 |
| `slack_get_user_profile` | ユーザープロフィールの取得 |

## Level 2: 確認許可が必要（承認後にアクセス可能）

他者に影響する書き込み操作。実行前に対象チャンネル・内容をユーザーに提示し、承認を得ること。

| ツール | 用途 | 確認すべき内容 |
|---|---|---|
| `slack_post_message` | チャンネルへのメッセージ投稿 | 投稿先チャンネル名、メッセージ全文 |
| `slack_reply_to_thread` | スレッドへの返信 | 投稿先チャンネル名、返信先スレッド、メッセージ全文 |
| `slack_add_reaction` | リアクションの追加 | 対象メッセージ、リアクション名 |

## Level 3: アクセス不可

該当ツールなし（現時点でslack MCPに破壊的操作は存在しない）。

## 運用上の注意

### コンテキスト消費の制御

- `slack_get_channel_history` のレスポンスはメタデータ（attachments, blocks, files等）を含み非常に大きい
- `limit` はデフォルト10を基本とし、50以上は避ける。必要に応じて段階的に増やす
- 複数チャンネルへの並行リクエストはコンテキストを急速に消費するため、対象を絞ること
- レスポンスが大きすぎるとファイルに退避され、後続のGrep/Readで読み直す手間が発生する

### メッセージ検索の制約

- slack MCPにはメッセージ検索（キーワード検索）機能がない
- 特定トピックを探す場合は、関連チャンネルの履歴を取得→ローカルでGrep、という手順になる
- チャンネル履歴は新しいものから返るため、古い議論は `has_more: true` で追加取得が必要

### チャンネルアクセス

- 未参加チャンネルは `not_in_channel` エラーで履歴取得不可
- 参加済みチャンネルは `slack_list_channels` のレスポンス内 `is_member: true` で判別可能
### スレッドの活用

- メッセージの `thread_ts` と `reply_count` でスレッドの存在・規模を判断できる
- 関心のあるトピックはスレッド単位で `slack_get_thread_replies` を使うのが効率的（チャンネル全体より軽量）

## 補足

- Level 2のツールはMCP経由での投稿取り消し手段がないため不可逆である
- テスト目的の投稿は `notify_test`（`C0L26FS03`）を使用すること
